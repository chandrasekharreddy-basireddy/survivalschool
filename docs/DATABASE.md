# Database

PostgreSQL 16, accessed via SQLAlchemy 2.0's async ORM (`asyncpg` driver at
runtime, `psycopg2` for Alembic's synchronous migration path). Schema is
managed entirely through Alembic — there is no separate hand-written DDL to
drift out of sync.

## Migrations

```
backend/alembic/versions/5ed05c6881ad_initial_schema.py
backend/alembic/versions/aedd5b33915f_add_composite_indexes_for_attempt_.py
backend/alembic/versions/8bc7896b64a9_add_certificate_skills_grade_score_.py
backend/alembic/versions/6f1ba11d04f8_add_timetable_discussions_practice_.py
backend/alembic/versions/31e4fc98f4cf_add_contests_ai_mock_practice_.py
```

The initial schema migration creates the original core tables; later migrations (15 in total, including a merge head) grow the schema to the current 66 tables. The second migration adds two composite
indexes — `(student_id, quiz_id, status)` on `quiz_attempts` and
`(student_id, exam_id, status)` on `exam_attempts` — found during a security/
correctness review: `start_attempt()`/`start_exam_attempt()` and
`current_attempt()` filter on exactly that column triple on every attempt
start/resume, and previously only had single-column indexes on each part
individually, forcing Postgres to intersect two indexes or scan-filter one.
The third adds `grade`, `score_percent`, `skills_json`, `specialization`,
`instructor_name`, `expires_at` to `certificates`, and `skills`,
`specialization` to `courses` — the columns backing the certificate-system
rebuild described in `docs/STATUS.md`. Autogenerate omitted a
`server_default` on the two new `JSON NOT NULL` columns (`skills_json`,
`skills`), which would have failed applying against any table with existing
rows; both were manually given `server_default='[]'` in the migration file
before applying, since autogenerate's output is a starting point, not
something to apply blindly.

The fourth migration adds `fullscreen_required` and
`integrity_monitoring_enabled` to `exams`, plus the 10 tables backing
contests, AI mock practice, and attendance described below.

All four migrations were generated by `alembic revision --autogenerate`
against the actual model definitions and applied to a real local Postgres
instance (`alembic upgrade head`) during this build — the schema in the
database and the schema in `app/models/*.py` are confirmed in sync, not just
assumed to be.

To add a new migration:

```bash
cd backend
alembic revision --autogenerate -m "describe the change"
# review the generated file — autogenerate is a starting point, not gospel
alembic upgrade head
```

## Table inventory (66 tables, by domain)

**Identity & access** (`app/models/user.py`): `users`, `roles`, `permissions`,
`role_permissions`, `user_roles`, `profiles`, `email_verifications`,
`password_resets`, `refresh_tokens`, `sessions`.

**Courses & progress** (`app/models/lms.py`): `courses`, `course_sections`,
`lessons`, `lesson_resources`, `enrollments`, `lesson_progress`,
`course_progress`.

**Assessment engine** (`app/models/assessment.py`): `questions`,
`question_options`, `quizzes`, `quiz_attempts`, `quiz_answers`, `exams`,
`exam_attempts`, `exam_answers`.

**Gamification** (`app/models/gamification.py`): `points`, `streaks`,
`badges`, `achievements`, `leaderboards`.

**Certificates** (`app/models/certificate.py`): `certificates`.

**Social / chat / notifications** (`app/models/social.py`): `chat_rooms`,
`chat_members`, `chat_messages`, `message_reads`, `notifications`,
`notification_preferences`.

**AI assistant** (`app/models/ai.py`): `ai_conversations`, `ai_messages`.

**System** (`app/models/system.py`): `analytics_events`, `audit_logs`,
`support_tickets`, `files`, `system_settings`.

**Timetable** (`app/models/timetable.py`): `timetable_entries` — course,
instructor (nullable, `SET NULL` on instructor deletion so a schedule
survives an account removal), term/term dates, day-of-week, start/end time,
room, session type. Composite index on `(term, day_of_week)`.

**Discussions** (`app/models/discussion.py`): `discussion_threads`,
`discussion_replies`, `discussion_votes` (unique on `(thread_id, user_id)` —
one vote per user per thread, enforced at the database level, not just the
API).

**Practice mode** (`app/models/practice.py`): `question_bookmarks` (unique on
`(student_id, question_id)`), `practice_sessions`, `practice_answers`.
Practice sessions are intentionally separate tables from `quiz_attempts`/
`exam_attempts` rather than a reused/overloaded attempt table — they carry no
gamification points and no pass/fail semantics, and keeping them structurally
distinct means a bug in quiz/exam scoring logic can't accidentally leak into
practice mode or vice versa.

Migration `6f1ba11d04f8_add_timetable_discussions_practice_.py` adds these 6
tables; applied and covered by `backend/tests/test_new_features.py` (14
tests, real Postgres/Redis). No `server_default` gotcha here — all six
tables are new, so there are no existing rows for autogenerate to break
against.

**Contests** (`app/models/contest.py`): `contests` (title, description,
contest_type, `occurrence_key` unique nullable — the idempotency key for
auto-generated occurrences — is_auto_generated, created_by nullable,
starts_at/ends_at, duration_seconds default 1800, `question_ids` JSON
snapshot of real `Question` IDs, top_n_awarded default 3, status
scheduled|open|closed, finalized_at), `contest_attempts` (unique on
`(contest_id, student_id)` — one attempt per student per contest —
question_order, started_at, server_deadline_at, submitted_at,
time_taken_seconds, score_percent, points_earned/possible, rank, status),
`contest_answers`, `contest_certificates` (deliberately a separate table
from `certificates` rather than reworking that model's `NOT NULL
course_id` — a contest win isn't tied to a course; unique on
`(contest_id, student_id)`, certificate_number unique, contest_title and
score_percent snapshotted at issuance, same reasoning as `certificates`).

**AI mock practice** (`app/models/ai_practice.py`): `ai_mock_sessions`
(student_id, subject, question_count, provider, submitted_at,
score_percent), `ai_generated_questions`, `ai_generated_question_options`,
`ai_mock_answers`. Deliberately a completely separate table set from
`questions`/`question_options` — no shared foreign key or code path — so
AI-generated content can never be merged with or mistaken for the real,
instructor-authored question bank used by quizzes/exams/contests.

**Attendance** (`app/models/attendance.py`): `attendance_sessions` (one
concrete calendar-date occurrence of a `TimetableEntry`; unique on
`(timetable_entry_id, session_date)`; opened_by, opened_at, check_in_code,
code_expires_at, closed_at), `attendance_records` (unique on `(session_id,
student_id)`; status present|absent|excused, method code|manual,
checked_in_at, marked_by).

Migration `31e4fc98f4cf_add_contests_ai_mock_practice_.py` adds these 10
tables plus `fullscreen_required`/`integrity_monitoring_enabled` on `exams`;
applied and covered by
`backend/tests/test_contests_ai_practice_import_integrity_attendance.py`
(12 tests, real Postgres/Redis).

## Design conventions

- **UUID primary keys everywhere** (`app/models/base.py::UUIDPk`) — no
  sequential integer IDs, so certificate numbers, enrollment IDs, etc. never
  leak ordering/volume information.
- **`created_at`/`updated_at` on every table** (`base.py::Timestamped`),
  server-defaulted so the database — not application code — is the source of
  truth for timestamps.
- **`ondelete="CASCADE"` on ownership foreign keys** (e.g. a deleted course
  cascades to its sections, lessons, quizzes) — verified structurally by the
  migration; exercised indirectly by the test suite's course/lesson fixtures,
  not by a dedicated cascade-delete test (a gap worth closing before a real
  delete-heavy admin flow ships).
- **`QuestionOption.is_correct`** is a real column but is a schema-layer
  concern to keep out of student-facing responses — see `docs/SECURITY.md`.
- **`quiz_attempts.question_order` / `exam_attempts.question_order`** store
  the randomized per-attempt question order as JSON, so re-fetching an
  in-progress attempt (autosave, page refresh) always reconstructs the exact
  same order the student started with rather than re-randomizing.
- **`exam_attempts.submission_client_token`** plus the `status` column
  together implement idempotent submission (see `docs/ARCHITECTURE.md`).
- **`analytics_events`** is deliberately append-only and never raises into
  the request that triggered it (`services/analytics_service.py`) — it feeds
  the Power BI dataset (`docs/POWERBI.md`) and is treated as best-effort
  telemetry, not transactional data.

## Connection pooling

`app/database.py` configures the async engine with `DB_POOL_SIZE` (default
10) and `DB_MAX_OVERFLOW` (default 20) in normal operation. When
`APP_ENV=test`, the engine switches to SQLAlchemy's `NullPool` instead — this
was a real bug fix during this build: pytest-asyncio's per-test event loops
were producing `RuntimeError: ... attached to a different loop` under a
pooled engine, because pooled connections were being reused across loop
boundaries. `NullPool` opens a fresh connection per checkout, which is
correct for a test suite's short-lived event loops and irrelevant for
production, where `APP_ENV=production` keeps normal pooling.

## Backups

`infra/scripts/backup_postgres.sh` does a logical `pg_dump | gzip` backup,
verifies the archive isn't truncated (`gzip -t`), and prunes anything older
than `RETENTION_DAYS` (default 14). `infra/k8s/11-backup-cronjob.yaml` runs it
nightly (03:00 UTC) as a Kubernetes CronJob against a dedicated
`postgres-backup-storage` PVC — deliberately a *separate* volume from
`postgres-data`, since a backup living on the same disk as the primary data
protects against nothing. Both are real and were verified end-to-end in this
session, not just written and assumed to work:

- Ran `backup_postgres.sh` against a live local Postgres instance — it
  produced a real `.sql.gz` file and passed its own integrity check.
- Validated `11-backup-cronjob.yaml` (and every other manifest in
  `infra/k8s/`) against the Kubernetes OpenAPI schema with `kubeconform
  -strict`: 25/25 resources valid.
- **A second, more thorough restore drill** (2026-08-14) went beyond a
  single row-count spot-check:
  1. Captured per-table row counts and a specific known row's exact field
     values (`admin@survivalschool.dev`'s email/name/2FA-status) from the
     live source database before touching anything.
  2. Ran the real `backup_postgres.sh` end-to-end, producing a genuine
     20,927-byte `.sql.gz` archive.
  3. Created a real, separate scratch database
     (`survivalschool_restore_drill`) and restored the archive into it with
     `gunzip -c backup.sql.gz | psql -v ON_ERROR_STOP=1` — exit code 0,
     zero errors in the restore log.
  4. Re-ran the exact same row-count query and known-row lookup against
     the restored database: **every table's count matched exactly**
     (`users`, `roles`, `permissions`, `role_permissions`, `courses`,
     `badges`, `profiles`), and the known row came back **byte-identical**.
  5. Confirmed `alembic_version` in the restored database matches the
     source exactly (`d18e6b4a3f57`) — the restored schema isn't just
     structurally similar, it's at the identical migration revision.
  6. Went further than a SQL-level check: **booted the real FastAPI
     application itself** against the restored database
     (`DATABASE_URL` pointed at `survivalschool_restore_drill`, nothing
     else changed) and confirmed `GET /api/v1/health` reported
     `"database": true` and `GET /api/v1/courses` returned real seeded
     course rows — proof the restored database isn't just queryable with
     `psql`, the actual application stack works against it unmodified.
  7. Tore down the scratch database afterward; nothing from this drill was
     left running.

**What this does NOT give you**, and what you still need to decide before
relying on it in production: off-site/cross-region copies (a PVC in the same
cluster is not disaster recovery — add a step that syncs `backup-storage` to
S3/GCS on a schedule), point-in-time recovery (this is periodic full dumps,
not continuous WAL archiving — use your cloud provider's managed Postgres
with PITR if you need RPO better than "since last nightly dump"), and a
recurring *restore drill* against a real production-sized dataset (the
verification above used the small seeded test dataset, not production
volumes or load). `infra/k8s/README.md` already recommends a managed Postgres
over the in-cluster StatefulSet for production — that guidance still stands;
treat this CronJob as the backup story for the self-hosted/staging topology,
and prefer your cloud provider's automated backups + PITR for the managed one.

## What has NOT been verified

- Behavior under real concurrent write load / lock contention has not been
  load-tested — the integration test suite runs sequentially against a
  single local Postgres instance.
